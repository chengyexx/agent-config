# AI 输出：好读、可决策、不丢关键信息

调研日期：2026-10-27。范围：通用可读性 + 开发场景的“只留核心文件/接口”。

## 结论

可读性和信息保全是会互相拉扯的目标。有效做法不是找一个万能提示词，而是：

1. **先分级**：P0 契约/行为，P1 影响面，P2 噪音。
2. **先排序再写**：用确定性信号（AST diff、调用图、API surface）算显著性，硬截断。
3. **按固定顺序解释**：为什么 → 是什么 → 影响谁 → 你要做什么。
4. **独立验收**：P0 recall、噪声率、skip list 诚实度。

## 开发场景：什么算核心

| 级别 | 判据 | 例子 |
|---|---|---|
| P0 必看 | 对外契约或行为变了 | 公开 API/路由/导出签名、请求响应字段、错误码、DB migration、配置/权限/安全 |
| P1 按需 | 直接影响但可后看 | 跨文件调用方、错误处理/重试/超时、测试与 fixture |
| P2 不写 | 无决策价值 | 格式化、重命名、注释、生成代码、lockfile、无外部引用的私有 helper |

接口只保留“契约级”：改了这个，别人必须跟着改的东西。

## 排序信号

| 信号 | 加分 |
|---|---|
| 公开/导出 API、路由、schema | +3 |
| 入口函数（变更集内无调用方） | +3 |
| 行为变化（非 rename/format） | +2 |
| 有变更集外的调用方 | +2 |
| 安全/配置/迁移 | +3 |
| 仅格式化/生成/无引用私有函数 | 排除 |

工具：diffsitter / GumTree（语义 diff）、oasdiff（API 破坏性变更）、code-review-graph（调用图 / blast radius）。

## 解释模板

```text
path:line · symbol()
变更：签名/行为/契约（≤1 行）
为什么：触发原因/意图（≤2 行）
影响：谁调用/哪个入口/是否破坏（≤1 行）
动作：需要你确认/改/跑什么（≤1 行）
```

规则：

- 先 why，后 what。
- 一行一个意思，尽量 ≤25 字。
- 只贴签名差异，不贴完整代码。
- 影响写“谁 + 数量”，不写“相关模块”。
- 不确定标“未确认”。
- 最后列“省略了什么及原因”；P0 不许省略。

## 输出契约

```text
硬预算：≤5 个文件、≤8 个符号、≤400 字。
判定优先级：P0 契约/行为/安全/配置/迁移 > P1 调用链影响 > P2 测试。
格式化、重命名、生成文件、锁文件，一律不写。
```

## 验收

| 检查 | 通过标准 |
|---|---|
| P0 recall | 用 API diff + 调用图生成 ground truth，P0 必须 100% 出现 |
| 噪声率 | 非 P1/P2 项 ≤20% |
| skip list | 声称省略的项与实际省略的 P0 不冲突 |
| 人工 | 30 秒内定位关键变更；3 题（改了什么/影响谁/怎么验证） |

不要用同一个模型给自己打分：LLM judge 有自偏好和长度偏置。

## 已知反模式

- “请简洁”压不住过度生成；要硬预算 + 固定结构 + 必留清单。
- 格式 ≠ 理解：JSON/Markdown 只改外形；给人看用散文/表格，给程序看才用 schema。
- CoT 不是免费：推理与交付分开，最终答案单独成段。
- 长上下文中间易丢：关键信息放开头/结尾，长文分块并复述。
- 变更说明不是全量文档：先问“读者要做什么决策”，再决定写多少。
